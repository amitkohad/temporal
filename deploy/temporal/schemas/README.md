# Database privilege and connection contract

All database mutations are separate operator actions. Current Azure PostgreSQL is Entra-only; no password authentication, application login, schema, or cloud credential is created by these files.

## Privilege bootstrap

An Entra database administrator executes roles.sql once in temporal and once in temporal_visibility, then reruns it after schema migrations to make schema_version/schema_update_history read-only to runtime. The script refuses other databases. Role pairs are temporal_migrator/temporal_runtime and temporal_visibility_migrator/temporal_visibility_runtime. These are password-free NOLOGIN privilege roles, not authentication principals. PUBLIC loses database CONNECT/TEMP, public schema CREATE/USAGE, and function EXECUTE. Runtime receives CONNECT, public USAGE, table SELECT/INSERT/UPDATE/DELETE, sequence USAGE/SELECT, and schema function EXECUTE. Migration receives database CONNECT and public CREATE; it owns objects through an explicit SET ROLE. Its default privileges grant runtime access to newly created schema objects. Separate nexusflow_migration schema is owned by the migrator and inaccessible to runtime/PUBLIC; the migration wrapper stores intent/partial-failure guards there.

Each login principal must receive only its matching store/operation role without ADMIN OPTION. It must not inherit database owner, Azure administrator, migration, or the other store's role. For PostgreSQL 17, grant membership with INHERIT FALSE and SET TRUE, then establish the startup role explicitly. SQL tool connect attributes can pass URL-encoded options=-c role=temporal_migrator (or matching visibility role); psql uses PGOPTIONS with the same role. Without SET ROLE, objects/default privileges belong to the login principal rather than the intended migrator. Do not make a runtime principal an owner. New databases come from Terraform; neither privilege role receives database CREATE/TEMP or CREATEDB. The administrator precreates BTREE_GIN in the visibility database because trusted extension installation requires database CREATE.

Run isolated fixture tests as a disposable PostgreSQL superuser only: apply roles.sql to both existing test databases, then roles-test.sql in each. The fixture verifies runtime DML, denied CREATE/ALTER/TEMP, denied migration-role escalation, and denied cross-store CONNECT. It creates/drops only nexusflow_role_fixture and does not prove Azure authentication. Never run test fixtures against Azure or production.

## Azure Entra mapping and renewable authentication

From an Entra administrator connection to the postgres database, create a nonadministrator managed-identity login with pg_catalog.pgaadauth_create_principal_with_oid(identity_name, object_id, 'service', false, false), after the object ID and tenant are verified; it avoids mutable display-name lookup. Grant it only its NOLOGIN role. Use separate identities for runtime and migration; workload identity trust and database grants are distinct controls. See [Microsoft managed-identity authentication](https://learn.microsoft.com/en-us/azure/postgresql/security/security-connect-with-managed-identity). entra-principal.sql provides the administrator mapping with identity_name, verified object_id, tenant_id and one allowlisted privilege_role; it rejects administrator-capable application identities. The database access token is passed as a password, expires, and must be renewed before new authentication.

This fork already supports SQL passwordCommand with PostgreSQL CreateRefreshableConnection: each new physical connection rebuilds its DSN and calls ResolvePassword. Runtime can therefore use a source-built executable that acquires a fresh workload-identity token through passwordCommand, without enabling password authentication. The new cmd/tools/entra-token helper exchanges fresh workload assertion files at fixed Azure OAuth endpoints, validates a minimum five-minute lifetime, and returns only the token on stdout. Compile it from the same immutable release source and package /usr/local/bin/entra-token into the runtime and schema executor before use. The current Phase 4 distroless image does not include it. Validate workload trust, identity-to-role mapping, renewal over expiration, stderr redaction, and MaxConnLifetime before deploying Entra runtime. Do not store a fixed Entra token as a long-lived Secret. The SQL tool CLI only receives a fixed SQL_PASSWORD per invocation, so bounded migration jobs must acquire a fresh token at invocation and reject insufficient remaining lifetime.

The selected design keeps Azure Entra-only authentication. Four distinct managed identities map to the two runtime and two migration roles. No PostgreSQL password login or long-lived credential Secret is created. OAuth tokens exist only in the bounded helper output/connection process environment and are never persisted, passed in argv, placed in Terraform or logged.

## TLS and identity references

The SQL tool uses SQL_PLUGIN=postgres12_pgx, SQL_HOST=the actual database certificate FQDN, SQL_PORT=5432, SQL_DATABASE matching the store, SQL_USER matching its login, SQL_PASSWORD containing a freshly acquired short-lived Entra token only in the connection process environment, SQL_TLS=true, SQL_TLS_CA_FILE=/etc/temporal/postgresql/ca.crt, SQL_TLS_DISABLE_HOST_VERIFICATION=false. A single SQL_TLS_SERVER_NAME override is not sufficient: the PostgreSQL driver uses the connection hostname for verify-full and does not use auth.TLS.ServerName when building its DSN. Keep SQL_HOST as the verified DNS name; private DNS resolves it to the private endpoint/subnet.

The driver maps TLS.Enabled plus EnableHostVerification to sslmode=verify-full, and CaFile to sslrootcert. ConnectAttributes take precedence over those fields. Disallow sslmode/sslrootcert/host/hostaddr overrides and unreviewed parameters; only explicit role options, connect_timeout and application_name are permitted by connection-policy.py. Runtime configuration uses tls.enabled=true, tls.enableHostVerification=true, tls.caFile at the mounted CA, and a certificate FQDN connectAddr. Test invalid CA and a mismatched DNS name against an isolated TLS database; configuration validation alone does not prove either rejection.

|---|---|---|
| Persistence migration | temporal-persistence-migration-identity ConfigMap | postgresql-principal-name, tenant-id, client-id |
| Visibility migration | temporal-visibility-migration-identity ConfigMap | postgresql-principal-name, tenant-id, client-id |

| Trusted PostgreSQL CA | temporal-postgresql-ca ConfigMap | ca.crt mounted /etc/temporal/postgresql/ca.crt read-only |

References require actual verified identity mappings before execution. Migration identities federate only to their per-store migration ServiceAccounts. Runtime identities federate to the runtime ServiceAccount and have no migration role. Assertions are projected, rotated files; the helper reads them afresh for every connection. CA material is public trust data; verify the actual issuer/fingerprint and rotation overlap before use. Client certificate/key flags must not imply unsupported PostgreSQL mTLS. The schema Job templates remain suspended until their executor image, immutable release bundle, identities, private TLS route and backup prerequisites are qualified.

Run connection-policy.py with the nonsecret SQL environment to reject TLS weakening and incorrect role selection. It prints no password/token. --allow-local-test permits a controlled local hostname/IP for isolated tests; it does not disable verify-full or CA validation. The schema wrapper must call this check and avoid echoing its environment.
Entra mapping references the service-principal object ID (not application client ID), fixes type to service, and validates existing object/tenant/admin status before granting. Four separate identities are required for the four store/operation roles. Runtime examples require distinct verified --client-id UUID arguments for the two stores. Both runtime identities may federate to the same runtime ServiceAccount, while each migration identity uses only its separate migration ServiceAccount. CLI overrides select a UUID only; tenant, assertion projection and fixed Azure endpoints remain unchanged. Existing baseline PasswordCommand hooks were verified at 717f485c760d1068aa310906466468e51120254f. BTREE_GIN is an Azure allowlisted trusted extension; administrator installation does not require application superuser privileges.

Role bootstrap explicitly grants its existing administrator membership in the migrator role so Azure's nonsuperuser administrator can configure role-owned default privileges. This grant belongs only to the bootstrap administrator; application principal mapping refuses any extra memberships and reuse of an object ID under another login. Never run bootstrap as a runtime principal.

Role bootstrap fails if an existing privilege role inherits another role or runtime owns any table/schema/database. Repair or transfer contaminated ownership only through a separately reviewed administrator action; a grant script must not silently preserve runtime DDL through ownership.

Entra LOGIN admission receives CONNECT directly on its own store because privilege membership has INHERIT FALSE; SET ROLE then activates schema/DML grants. Principal mapping revokes direct rights on both Temporal stores before granting own-store CONNECT. The isolated roles-login-fixture.sql creates four password-free LOGIN identities for local trusted-socket tests. Parent integration must verify actual per-store login with PGOPTIONS startup role, migration ownership, runtime DML, denied audit writes/DDL/escalation, and failed cross-store connection; roles-login-verify.sql assumes a migrator-owned nexusflow_login_fixture table and an existing schema_version table. Test logins are not production principals and must be confined to a disposable database container.
